### 7.1 服务器选型：Lightsail 东京 vs EC2 东京（2026-11 结论）

**结论：执行节点用 Lightsail 东京 1GB；只有面板也要迁东京时才升到 Lightsail 2GB/4GB。EC2 留到"必须用 VPC/安全组/IAM/SSM/Spot/预留实例/Unlimited CPU"时再上。**

理由一句话：本项目节点**长期低 CPU、低流量、只要一台**，Lightsail 把"计算 + 磁盘 + 2TB 流量 + 公网 IPv4"打包成一个可预测月费；EC2 的同等规格要**按件叠加**（实例 + 公网 IPv4 $3.65/月 + EBS），1GB/2GB 档按需价比 Lightsail 贵 **约 2 倍**（年差 $100–158），只有 4GB 档配 3 年预留或 Spot 才追平。

| 项目（东京，2026-11 实测价目核对） | Lightsail 东京（打包价） | EC2 东京（t4g / arm64 / 按需，**同容量磁盘**） |
| --- | --- | --- |
| 1GB 档 / 月 | **$7**（2 vCPU / **40GB SSD** / **2TB** 流量 / 含 IPv4） | t4g.micro **$7.88** + IPv4 **$3.65** + 40GB gp3 **$3.84** = **$15.37** |
| 2GB 档 / 月 | **$12**（60GB / 3TB） | t4g.small **$15.77** + $3.65 + 60GB **$5.76** = **$25.18** |
| 4GB 档 / 月 | **$24**（80GB / 4TB） | t4g.medium **$31.54** + $3.65 + 80GB **$7.68** = **$42.87** |
| 流量 | 2–4TB 额度（入+出都计入），日本超额 $0.14/GB | 入站免费；出站 $0.114/GB（每月 100GB 免费额度） |
| 公网 IP | 静态 IP 附着时免费 | 每个公网 IPv4 **$0.005/h = $3.65/月**（含弹性 IP） |
| 备选档位 | IPv6-only：1GB **$5**、512MB **$3.50** | t4g.nano（0.5GB）$3.94 + $3.65 + EBS |
| CPU 模型 | 突发型（基线约 5–10%，**无 Unlimited 模式**），持续高负载会降频 | t3/t4g 突发型，可开 **Unlimited**（超额另计费） |
| 停止计费 | **停止仍按月计费**，删掉才停 | 停止不计实例费；EBS/IP/快照继续计费 |
| 网络与权限 | 只有简易防火墙；不能挂 IAM Role；VPC 只能对等默认 VPC | 安全组、私有子网、IAM Role、SSM Session Manager（可不暴露 22）、CloudWatch 告警+自动恢复 |
| 省成本手段 | 无 RI/Spot/Savings Plans | 1 年预留 ≈ −37%（micro $4.96/月）；Spot ≈ −64~76%（micro $1.90/月） |
| 升级/迁移 | 快照可**导出成 EC2 实例** | 换实例类型即可（Arm↔x86 需换 AMI） |
| 运维复杂度 | 低（控制台 5 分钟起一台） | 中（VPC/EBS/SG/AMI 都要自己拼） |

**差距量化（同容量、东京、含磁盘与 IPv4）**：

| 场景 | Lightsail / 月 | EC2 按需 / 月 | EC2 1 年预留 / 月 | EC2 Spot / 月 |
| --- | ---: | ---: | ---: | ---: |
| 执行节点 1GB | **$7.00** | $15.37（**+120%**） | $12.45（+78%） | $9.39（+34%） |
| 面板+节点 2GB | **$12.00** | $25.18（**+110%**） | $19.34（+61%） | $14.08（+17%） |
| 重型 4GB | **$24.00** | $42.87（**+79%**） | $31.19（+30%） | $19.29（**−20%**） |

一年总账（按需、含 40/60/80GB 盘）：1GB 档 **Lightsail $84 vs EC2 $184（+$100/年）**；2GB 档 **$144 vs $302（+$158/年）**；4GB 档 **$288 vs $514（+$226/年）**。

差距主要来自**三笔摊开卖的附加费**，而不是实例本身：1GB 档里 t4g.micro 的 **$7.88 已经≈ Lightsail 全包价 $7**，但 IPv4（$3.65）+ EBS（$3.84）又叠加了 $7.49——几乎再买一台 Lightsail。

**结论（钱的角度）**：1GB/2GB 档 Lightsail 完胜，别为省事去买 EC2；只有到 **4GB 且用 3 年预留或 Spot** 时，EC2 才追平甚至反超（4GB 3 年预留 ≈ $24.98/月，Spot ≈ $19.29/月）。所以"先 Lightsail 1GB、长大再迁 EC2"在成本上也是对的。

**两条容易被忽略的钱**：

- EC2 的**公网 IPv4 单独收费**（$3.65/月）——对 t4g.micro 来说相当于再涨 46%，这也是 Lightsail 在 1GB 档几乎必胜的原因。
- Lightsail **停止实例仍然收费**（官方计费 FAQ），别指望"关机省钱"；EC2 反而可以随时 stop 省钱。

**什么情况下改选 EC2**：

1. 需要把执行节点放进已有 VPC、用安全组/私有子网做网络分区；
2. 需要 IAM Role 让节点读 S3/Secrets Manager 而不落地密钥（合规）；
3. 需要 SSM Session Manager 完全不开 22 端口；
4. 需要 CloudWatch 告警 + 自动恢复（无人值守的交易节点很实际）；
5. 需要 Spot/预留把长期成本压到 Lightsail 以下（通常要 ≥2GB 才明显）；
6. CPU 长期 >20%（Lightsail 无 Unlimited，会被限频）。

**推荐落地形态**：

- 采购：Lightsail 东京、Ubuntu 24.04、1GB plan、静态 IP；开自动快照（保留 7 天，$0.05/GB·月）。
- 网络：防火墙只开 `22`（限你的 IP）与 `51820/udp`（仅 `81.71.71.131`）；**不要开 80/443**，面板仍留广州。
- 若日后面板也迁东京：用 Lightsail **2GB**（`pnpm build` 峰值内存约 1GB，1GB 会 OOM）。
- 出问题再迁：Lightsail 快照可导出 EC2；届时用 t4g.small + 1 年 Savings Plan + 安全组 + SSM。

### 7.7 成本模型：滑点 + 手续费 + 资金费（2026-11-18）

统一在 `src/gridtrade/strategy/costs.py` 的 `CostModel`（frozen dataclass，单位 bp）：

| API | 含义 |
| --- | --- |
| `round_trip_bp(*, entry_taker, exit_taker, hold_hours, position_side)` | 一次开+平的总成本：进出手续费 + 双侧滑点 + 持有期资金费（空头符号相反） |
| `breakeven_spacing_bp(...)` | 保本间距 = `max(0, abs(round_trip_bp))` |
| `net_edge_bp(spacing_bp, ...)` / `is_profitable(...)` | 网格间距减去成本后的净边际 / 是否为正 |
| `describe()` | 参数 + 典型往返成本（maker/taker、0h/1h/8h）+ 保本间距，直接进 artifact/snapshot |

落地位置：

| 层 | 变化 |
| --- | --- |
| **网格策略** | `GridParams.min_edge_bp`（默认 0 = 不校验）；`>0` 且 `spacing <= round_trip + min_edge` 时 `on_start` 抛 `ValueError`；`describe()` 增加 `cost`；新增 `cost_report()`。**开多/开空本来就是库存式网格的天然行为**（`inventory=-level*size`，价格上行卖出建空、下行买入建多），无需方向开关 |
| **实时模拟盘** | 新增 `GRIDTRADE_PAPER_SLIPPAGE_BP`（默认 0.2）：买 `×(1+r)`、卖 `×(1−r)`，网格与止损都走同一 `_fill`；`paper_fills` 新增 `slip` 列（旧库自动 `ALTER TABLE` 迁移）；`snapshot()` 增加 `account.slippage`、每标的 `slippage`、`cost` 报告 |
| **实盘适配器** | 新增 `BINANCE_MAKER_FEE_BP/TAKER_FEE_BP/SLIPPAGE_BP` 假设，`health().cost` 输出 maker/taker 往返成本与保本间距；**实际手续费以成交 `commission` 为准**（面板"成交明细"显示 `commission`、`feeBp`、`realizedPnl`） |
| **面板** | `#/binance` 新增"成本模型（计划值）"卡片：maker 往返、taker 往返、资金费/8h、保本间距 |

实测：节点 `health().cost` → `round_trip_maker_bp=4.4`、`round_trip_taker_bp=10.4`、`breakeven_spacing_bp=4.4`（假设 maker 2bp / taker 5bp / 滑点 0.2bp）。

> 注意：**回测/模拟盘/实盘现在共用同一套成本口径**（`CostModel`），所以"网格间距 10bp 时 net edge 5.6bp"在三个环境里含义一致；差异只来自真实成交的费率与滑点。

### 7.9 K 线/行情延迟修复（2026-11-18）

**根因**：`/api/market/candles` 的实现在 `service.candles()` 里**只读本地 Parquet 数据集**，完全没有 live 路径；快照虽然会尝试 Binance，但广州主机到 `fapi.binance.com` 不通（TLS 被拦），最终 `source="dataset"`，K 线停在数据集最后一天（延迟数天）。

**修复**：把东京执行节点变成行情代理（它到 Binance 只有 2–4ms，且经 WireGuard 隧道与广州互通约 55ms）：

| 位置 | 改动 |
| --- | --- |
| 东京适配器 | 新增 `GET /market/candles`（`/fapi/v1/klines`）、`GET /market/funding`（`/fapi/v1/fundingRate`）、`GET /market/snapshot`（`premiumIndex` + `ticker/24hr`，全部公开接口） |
| 面板 `live.py` | 新增 `node_url` 支持：`node_candles/node_funding/node_snapshot`，K 线缓存 2s；`snapshot()` 在 live 关闭或失败时回退节点 |
| 面板 `service.py` | 新增 `market_candles()` / `market_funding()`：配置了节点且未指定历史区间时**优先走节点实时数据**，否则回退本地数据集 |
| 面板 `app.py` | `/api/market/candles`、`/api/market/funding` 改走 async 新方法；`LiveMarket` 注入 `settings.binance_node_url`；顺带修掉关闭时 `'LiveService' object has no attribute 'close'` |

**实测（广州面板 → 东京节点 → Binance）**：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| K 线来源 | `dataset`（数天前） | **`node`** |
| 最新 1m K 线滞后 | 数天 | **43 秒** |
| 面板请求耗时 | — | **0.144s**（隧道单程 ~55ms） |
| 快照 mark | 295.17（数据集收盘） | **282.15（实时）** |

> 说明：`GRIDTRADE_MARKET_LIVE` 仍可为 0（广州直连 Binance 依旧不可用），节点代理是独立路径；未配置 `GRIDTRADE_BINANCE_NODE_URL` 时行为与旧版完全一致（回退数据集）。
